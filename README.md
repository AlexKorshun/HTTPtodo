# HTTPtodo

Учебный сервис задач на Go: REST API на стандартном `net/http` (роутинг Go 1.22+, без фреймворков),
хранение в PostgreSQL через `pgx`, веб-интерфейс и вход по JWT.

Каждый пользователь видит и меняет только свои задачи. Регистрацией, паролями и выдачей токенов
занимается отдельный сервис [sso](../sso) — todo-api ходит в него по gRPC и проверяет подпись
токена локально.

## Возможности

- Регистрация и вход прямо в веб-интерфейсе
- Список задач, создание, отметка «выполнено», удаление
- Задачи изолированы по пользователям: чужая задача недоступна даже по прямому `id`

## Как устроено

```
браузер ──HTTP──► todo-api ──gRPC──► sso
                     │
                     ▼
                 PostgreSQL
```

- `POST /auth/register` и `POST /auth/login` — тонкие прокси в sso: todo-api сам пароли
  не хранит и не проверяет, он лишь передаёт запрос и возвращает выданный токен.
- Остальные ручки закрыты middleware: он разбирает `Authorization: Bearer <token>`,
  проверяет подпись общим секретом, срок действия и то, что токен выдан **этому** приложению
  (`app_id`), после чего кладёт `uid` в контекст запроса.
- Ниже по слоям `userID` едет обычным аргументом и в итоге попадает в `WHERE user_id = $1`.

Слои и зависимости — внутрь, через интерфейсы, объявленные у потребителя:
`httpapi` (`TaskService`, `SSOClient`) → `service` (`Storage`) → `repository/postgres`.

## Требования

- Go 1.26+
- Docker (для PostgreSQL)
- [goose](https://github.com/pressly/goose): `go install github.com/pressly/goose/v3/cmd/goose@latest`
- Запущенный сервис sso — без него не работают регистрация и вход

## Быстрый старт

```bash
# 1. Настроить окружение
cp .env.example .env      # и подставить реальные значения, см. таблицу ниже

# 2. Поднять PostgreSQL (порт 5432)
docker compose up -d

# 3. Накатить схему
export $(grep -v '^#' .env | xargs)
goose -dir migrations postgres "$DATABASE_URL" up

# 4. Запустить
go run ./cmd/httptodo
```

Открыть **http://localhost:8080** — там форма входа, аккаунт создаётся кнопкой
«Зарегистрироваться».

Перед первым входом sso должен знать про это приложение: в его таблице `apps` нужна строка,
`secret` которой совпадает с `APP_SECRET` ниже, а `id` — с `APP_ID`. Как её добавить, описано
в README самого sso.

## Переменные окружения

Читаются из окружения и из `.env`, если файл есть. Все обязательны.

| Переменная     | Пример                                              | Описание |
|----------------|-----------------------------------------------------|----------|
| `DATABASE_URL` | `postgres://postgres_user:secret@localhost:5432/todo` | подключение к PostgreSQL |
| `PORT`         | `8080`                                              | порт HTTP-сервера |
| `APP_SECRET`   | `secret`                                            | ключ подписи JWT, общий с sso |
| `APP_ID`       | `2`                                                 | идентификатор приложения в таблице `apps` sso |
| `SSO_ADDRESS`  | `localhost:44044`                                   | адрес gRPC-сервера sso |
| `SSO_TIMEOUT`  | `5s`                                                | таймаут одного вызова sso |
| `SSO_RETRIES`  | `3`                                                 | число повторов при недоступности sso |

`APP_SECRET` и `APP_ID` должны совпадать со строкой в таблице `apps` сервиса sso — иначе
подпись токена не сойдётся и все защищённые запросы будут отвечать `401`.

## API

Базовый URL: `http://localhost:8080`

Открытые:

| Метод  | Путь              | Тело                              | Ответ |
|--------|-------------------|-----------------------------------|-------|
| `POST` | `/auth/register`  | `{"email": "...", "password": "..."}` | `201` — `{"user_id": 1}`; `409` если email занят |
| `POST` | `/auth/login`     | `{"email": "...", "password": "..."}` | `200` — `{"token": "..."}`; `401` если пара неверна |
| `GET`  | `/`               | —                                 | веб-интерфейс |

Требуют заголовок `Authorization: Bearer <token>`:

| Метод    | Путь          | Тело              | Ответ |
|----------|---------------|-------------------|-------|
| `GET`    | `/tasks`      | —                 | `200` — массив задач пользователя |
| `POST`   | `/tasks`      | `{"text": "..."}` | `201` — созданная задача |
| `PATCH`  | `/tasks/{id}` | —                 | `200` — задача с переключённым `done` |
| `DELETE` | `/tasks/{id}` | —                 | `204` |

Без токена или с чужим/просроченным — `401`. Обращение к чужой задаче — `404`
(а не `403`: иначе ответ подтверждал бы, что такая задача существует).

Ошибки возвращаются как `{"error": "описание"}`.

### Пример через curl

```bash
curl -X POST localhost:8080/auth/register -d '{"email":"me@test.com","password":"secret123"}'
TOKEN=$(curl -s -X POST localhost:8080/auth/login \
  -d '{"email":"me@test.com","password":"secret123"}' | jq -r .token)

curl -X POST localhost:8080/tasks -H "Authorization: Bearer $TOKEN" -d '{"text":"купить хлеб"}'
curl localhost:8080/tasks -H "Authorization: Bearer $TOKEN"
```

## Развёртывание

Фронтенд вшит в бинарник через `//go:embed`, поэтому на сервер едет один файл — рабочий
каталог и наличие папки `web/` значения не имеют.

```bash
go build -o httptodo ./cmd/httptodo
```

Дальше на сервере: положить бинарник, задать те же переменные окружения (через `.env` рядом
или средствами systemd/Docker), накатить миграции на боевую базу тем же `goose`, запустить.

Три вещи, без которых наружу выставлять нельзя:

1. **Сменить `APP_SECRET`** на длинную случайную строку — и одновременно в строке `apps`
   сервиса sso. Значение из примера знает кто угодно, кто видел этот репозиторий.
2. **Включить HTTPS** (обычно nginx или Caddy перед сервисом). Токен ездит в заголовке и
   лежит в `localStorage` браузера — по голому HTTP его перехватят.
3. **Указать реальный `SSO_ADDRESS`** — sso должен быть доступен с машины, где работает
   todo-api, и желательно не торчать в интернет.

## Структура проекта

```
cmd/httptodo/main.go            точка входа: сборка зависимостей
internal/
  api/httpapi/                  HTTP-слой
    routes.go                   маршруты, middleware только на /tasks
    middleware.go               разбор JWT, userID в контексте
    auth.go                     /auth/register и /auth/login (прокси в sso)
    tasks.go                    хендлеры задач
    respond.go, httpserver.go   ответы и запуск сервера
  clients/sso/grpc/             gRPC-клиент к sso (retry + логирование)
  service/                      бизнес-логика, интерфейс Storage
  repository/postgres/          реализация Storage на pgx
  model/                        модели и sentinel-ошибки
  config/                       чтение конфигурации из окружения
migrations/                     SQL-миграции (goose)
web/                            index.html + embed
docker-compose.yml              PostgreSQL для локальной разработки
```
